## Investigation summary

1. **Create → "must load" cause.** The Create success branch never set `window.retestLoadedProposal`, so the Update button (shown only when a proposal is loaded) stayed hidden after Create. A second Create then hit the Phase 1G duplicate-name rejection, whose text is "A proposal named … already exists … Load that proposal and use Update, or change the customer name or proposal date." That is the "must be loaded" message. No frontend string says it; it comes from the backend.
2. **Is a backend change needed?** No. The managed Create response already carries `proposalId`, `currentRevision`, `baseName`, `docId`, `pdfFileId`, `googleDocUrl`, `pdfUrl`, which is everything Update's preconditions use (`proposalId`, integer `currentRevision`, `destinationFolderId` which the frontend already holds, `baseName`, file links).
3. **Why Load "disappears".** Measured in headless Edge with the real Tailwind CSS. Nothing hides it. The export controls sit in one non-wrapping flex row inside a `<details overflow-hidden>`; once the status text, Doc/PDF links, Update button and loaded indicator are present, the row overflows and is clipped. Before the fix (`v10.01.1`): at 800px, Load, Update and Create were all clipped after a Load; at 1024px Create was clipped after a Load; at 420px Load was clipped right after a Create.
4. **Other facts traced.** Update uses the stored `retestLoadedProposal` identity, not the destination dropdown. `masterNewQuote` is wrapped to clear `retestLoadedProposal`, the indicator and the loaded links. Loading another proposal already replaces the loaded identity (with snapshot/rollback).

## Changes made

All in `Agent/retest.html` (mirrored to `retest.txt`):

- **New `window.establishLoadedProposalFromCreate(resp, destinationFolderId, builderState)`** in the Load script block. On a valid managed Create response it sets `retestLoadedProposal` (`proposalId`, `currentRevision`, `destinationFolderId`, `baseName`, `currentFiles` mapped from the Create response, `loadedAt`, `loadedBuilderState` clone), refreshes the indicator (which also shows the Update button) and registers the Doc/PDF links so New Quote clears them. It never throws and returns false on a malformed response, so a created proposal is never reported as failed.
- **Create success branch:** one call to that function when `json.managed`. Nothing else in Create changed.
- **New `window.describeManagedCreateConflict(message, destinationFolderId)`** and one use in Create's `catch`. If the duplicate-name rejection names the proposal that is already loaded, the message becomes `"{name}" is already loaded. Use Update to save your changes as Rev {n+1}.` Any other error text is shown unchanged.
- **Update error handling:** when the backend returns `{success:false, error}` (other than `STALE_REVISION`), that text is shown instead of the generic "Unexpected update response".
- **Layout:** `flex-wrap` added to the export-controls row, and `whitespace-nowrap` replaced by `whitespace-normal break-words max-w-full` on the status text, so all controls wrap instead of being clipped.
- **Version:** v10.01.1 → v10.01.2 in the header comment (description now "Managed Create Loaded State"), `<title>`, both visible badges, and the `appVersion` and export-filename strings (same sites the previous release changed).

## Remaining caveats

- **Long requests.** Real Create and Update appear to take about a minute. A client that loses the connection sees "Failed to fetch" while the save may have completed on the server. After such a failure the proposal is not marked as loaded; a retry will be told the name already exists, and the correct path is Load then Update. A follow-up could check server state after a network failure.
- **Duplicate Doc name during Update.** While Update renders, two Docs briefly share the live name in `Proposal Docs`. After the real Update, the local Drive mirror shows the live Doc as `… - Proposal (1).gdoc`. This is probably only Drive for desktop's local alias for the transient duplicate. The cloud name (from `makeCopy(base, …)`) should be the clean base name, but this was not confirmed in the Drive web UI. Worth checking.
- **Throwaway proposal left in Drive** (`PROP-261001-5B7E8D`, Rev 2, files named for "Zz Loaded State Test", plus its Archive files and snapshot). It will appear in the Load list for `Test` until removed by hand.
- **Customer mismatch is not warned.** If a user edits the customer name on a loaded proposal and clicks Update, the proposal is updated in place and keeps its original base name. A confirmation warning when the customer differs from the loaded proposal is a possible future safeguard.
- The pre-existing `sanitizePage2HeaderSettings is not a function` error seen only on a first run in a clean browser profile was not touched.
