## Investigation result

### 1. Executive finding

**Most likely B, a successful backend Create whose response was lost before the browser could use it, with the break between Apps Script finishing and the browser receiving the redirect/echo response (touching D).** This is established far better than in the earlier investigation, because the proposal **does exist**.

- The 7:24:26 execution (13.19 s, Completed) produced `2026-10-01 - yeafg - Proposal` (`PROP-261001-572F8E`), confirmed by both the real backend's `listManagedProposals` and the Drive mirror. Doc modified 07:24:35, PDF 07:24:36, manifest `createdAt` 07:24:37.787 local, and no other write exists anywhere in the 07:20–07:30 window. Execution start 07:24:26 + 13.19 s = end about 07:24:39.2, so the write times fall inside that execution.
- The manifest records what the browser sent: `customerName: "yeafg"`, `address: "gaga"`, phone `4242`, email `2424`, date 2026-10-01, rows 91/92. It contains no "Zz" and no "Loaded State". It is Rev 1, `updatedAt == createdAt`, clean name `2026-10-01 - yeafg - Proposal`, destination `Test`.
- So the user's observation "no new proposal appeared" does not match Drive; it is likely they looked for a different customer name, or looked before sync caught up. This should be confirmed with the user (was the customer they typed at 7:24 "yeafg"?).
- The 7:20:44 execution (1.267 s) created nothing. It is too short and wrote nothing, so it was likely a quick call such as the folder list on page load; it cannot be identified from the evidence.

### 2. Request flow (from source)

1. Click `#btn-create-proposal` → `createProposalExportFromRetest()` (retest.html about line 24683): copies form into jobData, requires destination, date, name, address and `window.pureCopyText`.
2. Builds `builderState` (`proposalAppState`, `systemScratchpads`, `selectedProposalRows`) and payload `{action:'createProposalExport', destinationFolderId, proposalDate, customerName, address, zip, proposalText, builderState}`.
3. `fetch(API_URL, {method:'POST', headers:{'Content-Type':'text/plain;charset=utf-8'}, body: JSON.stringify(payload)})` (line 24745): simple CORS request (no preflight), default redirect `follow`. **No timeout, no AbortController, no retry, no custom redirect handling anywhere in the file.**
4. Apps Script `doPost` (script_changeout.gs 1859): parses body, dispatches on `action`; everything is inside one `try/catch` that returns `{success:false,error}` JSON, so a completed doPost always yields a 200 JSON body.
5. `createProposalExport` (2429), managed branch: validate fields → `validateProposalDestinationFolder` → `LockService.waitLock(15000)` → clean base name + `assertManagedProposalBaseNameAvailable` (5 name lookups) → `makeCopy` of the template into `Proposal Docs` → `DocumentApp.openById` + `replaceText` + `saveAndClose` → `getAs(PDF)` + `createFile` in the folder root → `generateProposalId` → manifest `createFile` in `Proposal Data` → response `{success, baseName, docId, googleDocUrl, pdfFileId, pdfUrl, managed:true, proposalId, currentRevision:1, manifestFileId}` → lock released.
6. `jsonResponse` = `ContentService.createTextOutput(JSON.stringify(obj)).setMimeType(JSON)`, a small body (well under 1 KB).
7. Apps Script web apps deliver that output via an HTTP 302 to `script.googleusercontent.com/macros/echo?...` which the browser follows with a GET. The execution's "Completed" and "Duration" cover only the script run, not these hops.
8. Browser: if `fetch()` rejects, control goes to the `catch` (line 24776), which prints the error text; if `response.ok` is false it throws `HTTP error! status: N`; otherwise `response.json()` then the success branch (the Loaded-Rev-1 logic runs only here, line 24766).

### 3. Evidence

**Facts established by code:**
- No frontend timeout/abort/retry exists.
- All backend exceptions are caught and returned as JSON; a normal run always returns a small JSON body.
- "Failed to fetch" is the text a browser gives when `fetch()` itself rejects (network error, reset, or a CORS-blocked response). It is not produced by the code's own errors: a non-2xx would read "HTTP error! status: N", a backend error would show its own message, a non-JSON body would show a JSON parse error, and a JavaScript exception after success would show that exception's text.
- Therefore the success branch, including the Loaded-Rev-1 logic, did not run on that click.
- The Create path has no stage logging (only `console.error` in the catch blocks), so internal stages cannot be recovered from logs.

**Evidence from the user's execution history and Drive:**
- A Completed 13.19 s doPost at 7:24:26 coincides with a full Create (Doc, PDF, manifest). A Completed execution at 7:20:44 (1.267 s) wrote nothing.
- Drive/backend list: the yeafg proposal exists, Rev 1, clean name; nothing else was created in that window.

**Reasonable inferences:**
- The browser lost the response of a request that the server completed. This is the same pattern seen twice in my own earlier real-Drive tests from headless Edge on this machine (Create: sent 06:46:34, server wrote manifest 06:46:44.7, client failed 06:47:23 with `ERR_CONNECTION_RESET`; Update: sent 06:48:33, server done 06:48:49, client failed 06:49:33 with `ERR_TIMED_OUT`). In both, the log showed the POST going out and **no redirect/echo request ever following**, i.e. the 302 never reached the browser. Two different browsers on the same machine showing the same behavior points at the network path or the Google front end for slower executions, not at the page code.
- Duration alone is not the trigger: the owner's Chrome completed a Create at 06:17 and an Update at 04:52 normally, and a first Edge Create attempt at 06:43 had no server effect at all. Something about the connection varies over time.

**Unknown:**
- The browser's actual failure code (`net::ERR_...`), whether a 302/echo hop was attempted, and whether the browser or an intermediate device dropped the connection. The live Chrome tab has no debugging port and I could not read its console or network panel.
- What the 7:20:44 execution was.
- Whether Apps Script returned any non-2xx at the redirect/echo stage (not visible in the Executions list).

### 4. The 13.19-second execution

- **Tells us:** the script ran to the end of the Create path. Drive stamps show Doc finalized about 9 s in (template copy plus text replace and save are the slow steps), PDF about 10 s, manifest at 11.8 s, end at about 13.2 s. That is consistent with an ordinary full Create (my own controlled Create took about 10 s) and with no Drive hang or failure.
- **Does not tell us:** whether the browser received a response, what HTTP status or redirect behavior the browser saw, or when and why the browser gave up. Duration excludes network transit and the redirect hop. It also does not prove the doPost came from the user's click alone, though the timing match and the absence of any other write make it very likely.

### 5. The Zz file

Unrelated to the latest attempt. `PROP-261001-5B7E8D` was created at 06:46:44 and updated at 06:48:48.9 by my controlled real-Drive test (documented in `2026-10-01_0652_v10.01.2-v16.52.1_Create-Loaded-State.md`), carries my edit markers, and predates the 7:20/7:24 executions by about 35 minutes. The browser sent "yeafg", not "Zz".

### 6. Deployment (Version 47 vs local v16.52.1)

- **Cannot be established directly.** Nothing in the project records deployment IDs or version numbers (searched), the Apps Script editor content is not readable from here, and no deployment tooling exists in the project.
- **Consistent with local source:** local `script_changeout.gs` was last modified 05:56:21 on Oct 1, before every observed Phase 1G behavior. The deployed endpoint produces clean names (`tester` 06:17, Zz 06:46, `yeafg` 07:24), Update archives `_v1` and snapshots, the manifest shape, and list/load behavior matching this source. Both executions list Version 47.
- **Not provable:** that the deployed text equals the local file byte for byte. A material difference in the Create path seems unlikely given the matching behavior, and in any case would not explain a response being lost.

### 7. Recommended next step

1. **Smallest distinguishing diagnostic (no code):** with Chrome DevTools open (Network tab, "Preserve log" on), click Create once more with a new customer name and read the `exec` request: its status or `(failed) net::ERR_...` text, its timing, and whether a 302 and a `script.googleusercontent.com/macros/echo` request follow. Alternatively capture `chrome://net-export`. This tells us in one attempt whether it is a reset/timeout before the 302 (network/gateway) or something at the redirect/echo step.
2. **Code change worth making regardless of root cause (not implemented here):** when a managed Create gets a network error, have the frontend check the backend with the read-only `listManagedProposals` for a proposal with the expected base name. If found, treat the Create as successful and establish the loaded Rev 1 state; if not, say plainly that nothing was created. Also log the error name and elapsed milliseconds to the console. That fixes the user-visible damage (a good save that looks like a failure, then a confusing "already exists" on retry) without depending on why the response was lost.
