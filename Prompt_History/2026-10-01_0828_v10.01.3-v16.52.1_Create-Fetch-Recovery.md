## Implementation summary

All changes are in `Agent/retest.html` (mirrored to `retest.txt`). About 205 lines added and 18 removed relative to the v10.01.2 checkpoint, of which 11 are version-stamp replacements.

1. **Create handler** (`window.createProposalExportFromRetest`):
   - Records the attempt start time, the loaded-proposal identity at that moment, the expected base name, and the exact `builderState` that was sent.
   - Flags a **transport failure** only when `fetch()` itself rejects, or when reading the response body dies with something other than a `SyntaxError`. HTTP-status errors, non-JSON bodies and backend `{success:false}` responses stay ordinary errors with their real messages, and the recovery path does not run.
   - On a transport failure it calls the recovery function and shows its message. Otherwise the existing error path is unchanged.
   - Logs error name, elapsed milliseconds and the transport flag to the console.
2. **`window.expectedManagedProposalBaseName(date, customer)`**: a client mirror of the backend `sanitizeProposalFilenamePart`, producing `{date} - {customer} - Proposal`. It was compared against the real `.gs` function on 12 tricky inputs (slashes, quotes, control characters, repeated hyphens, empty/null, non-ASCII).
3. **`window.recoverManagedCreateAfterNetworkFailure(ctx)`** (read-only; the Create POST is never re-sent):
   - Polls `listManagedProposals` for the selected destination, up to 4 lookups spaced 5 s apart and stopping 45 s after the send, because the server may still be finishing when the browser gives up.
   - Filters the list to the exact expected `baseName`.
   - Outcomes: `recovered`, `none` (safe to retry), `ambiguous` (more than one match, or the candidate does not verify), `older` (the same-name proposal predates this attempt), `unverified` (the lookup itself failed, so it does **not** claim safe to retry), `superseded` (the loaded proposal changed in flight).
   - A unique fresh candidate is adopted only after `getProposalState` verifies **all** of: `success` and `managed`; same `proposalId`; same `destinationFolderId`; `currentRevision === 1`; `currentFiles.baseName` equals the expected name; Doc and PDF both exist; `createdAt` is not earlier than this attempt (minus a 2-minute clock-skew allowance); and the stored `builderState` is **deeply equal to what was sent**.
   - On adoption it builds `window.retestLoadedProposal` from the verified state (real id, revision, files, timestamps, and the sent state as `loadedBuilderState`), updates the indicator (Update becomes available), restores the Doc/PDF links, and shows the recovery message.
4. **Status helper**: `showProposalExportStatus` also clears the interim amber colour used while checking. All recovery messages are set with `textContent`, so a customer name cannot inject markup.
5. **Versions**: header comment, `<title>`, navbar badge, `#page2-version-badge`, `appVersion` ×3 and the three export filenames all read v10.01.3. No `10.01.2` string remains.

## Remaining caveats

- **Not tested in a real browser against the real backend.** The mocks simulate a rejected `fetch` with a connection reset. A real run is needed to confirm the user's Chrome behaves the same way, and that the recovery lookup succeeds on the same flaky connection.
- **Recovery only helps if the lookup request itself gets through.** If the network is down for the lookup too, the user sees the "Do not retry yet… Use Load" message instead of auto-recovery.
- **Slow responses.** The browser can give up as late as about 49–59 s. The recovery then performs one lookup, since polling stops 45 s after the send.
- **Clock skew.** The attempt-time check tolerates 2 minutes of difference between the browser and Google's clock. A badly skewed device could see an older-than-expected `createdAt` and get the manual-review message.
- **Existing behaviour left as is:** the customer name is rendered unescaped by existing form/cart code (observed in testing when a name containing markup set a page flag before Create was even clicked). That is outside this task and unchanged.
- **Deployment:** the frontend is a local file; nothing was committed, pushed or deployed. The backend deployment ("Version 47") is unchanged and still cannot be proven equal to local v16.52.1.
- **Checkpoints:** none created for this task (Git is the history per `Changeout_Rules.md` §3). The earlier gitignored v10.01.2 checkpoint (`Agent/retest_v10.01.2_2026_10_01_0651.html/.txt`) was byte-identical to the source before this edit.
- The scratchpad test files are outside the project and will not exist in a new session.
