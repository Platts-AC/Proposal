## Evidence found

### Exact current Create flow (frontend v10.01.3)
- Payload: `{action:'createProposalExport', destinationFolderId, proposalDate, customerName, address, zip, proposalText, builderState}`; `builderState` is a JSON clone of `{proposalAppState, systemScratchpads, selectedProposalRows}`. Roughly 5 KB in practice (the five saved `builderState`s are 1.7–2.5 KB).
- Sent as `fetch(API_URL, POST, Content-Type: text/plain;charset=utf-8, body JSON)`. `text/plain` makes it a simple CORS request, so there is no preflight (this is the standard Apps Script pattern). It is identical in v10.00.0, v10.01.1, v10.01.2 and now, and no `fetch`/XHR override exists.
- Pre-send guards (same fields the backend requires) show "Missing Date, Name, Address…" locally, so a request that was never sent cannot be a backend "Missing" error.
- Outcome handling: `!response.ok` throws "HTTP error!"; a body-read failure that is not a `SyntaxError` and a rejected `fetch` set `transportFailure`; a backend `{success:false}` throws its own message. Only `transportFailure` starts recovery.
- Recovery starts the moment `fetch` rejects. The original request may still be running server-side if the browser gave up early; the recovery polls (up to 4 lookups, 5 s apart, until 45 s after the send) to cover that.

### Backend v16.52.1 Create path
`doPost` parses the body → `createProposalExport`. For a managed request: required-field check → `validateProposalDestinationFolder` (iterates the root folder's children) → `LockService` script lock (`waitLock` 15 s) → `assertManagedProposalBaseNameAvailable` (up to five name lookups) → template `makeCopy` → `DocumentApp` `replaceText` → PDF → manifest → JSON response. A failure after the Doc copy trashes the Doc/PDF/manifest and rethrows.

`doPost` wraps everything in `try/catch`; **any** exception becomes `console.error(err)` plus a normal `{success:false,error}` JSON response. Such an execution is therefore listed as **Completed**, not Failed.

### Backend exits that finish in about 1–6 s without writing a proposal
1. `Missing request body` / JSON parse failure: under about 1 s.
2. `Missing required proposal payload fields`: about 1.3 s (measured).
3. `Invalid proposal destination folder`: about 4 s (measured 3.9 s).
4. Duplicate-name rejection (`already exists…`): roughly 3–6 s (destination scan plus the lookups).
5. An exception after the Doc copy (template copy, `replaceText`, PDF conversion), followed by cleanup trashing: very roughly 5–10 s. This is the only no-write path that would leave a **trashed** Doc in Drive.
6. Lock timeout: at least 15 s, so not in the observed range.

Paths 1–4 return a readable JSON error. Paths 2–4 cannot explain this case: the browser blocks missing fields locally, the destination is valid, and no "FETCH RECOVERY TEST 1001" file exists anywhere in the local mirror (a duplicate would have been listed by recovery).
