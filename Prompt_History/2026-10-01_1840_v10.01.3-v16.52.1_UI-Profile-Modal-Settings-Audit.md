## Final Agent Report — Verbatim

The existing code already has most of what a shared modal-preferences system needs, but it is not the layout profile system. A dormant "user settings" layer in `retest.html` gives saved-override-else-default precedence, sparse overrides, resets and a config export, and nothing uses it yet. Layout profiles are a poor home for modal preferences. I changed no source, backend, proposal data or rules, and I made no commit, push or deploy. The only new file is this record. This was a static read of `retest.html` with no browser run and no live backend calls; counts come from searches.

## 1. Current profile architecture
- **Storage:** `changeout_profiles_v1` holds `{profileName: deep clone of the whole appState minus activeFilters, resultSort, resultLimit}`.
- **Functions** (in the profile manager, ~16190–16470):
  - `saveLayoutProfile`, `updateLayoutProfile`, `renameLayoutProfile` and `deleteLayoutProfile`, which use native `confirm`/`prompt`.
  - `loadLayoutProfile`, which assigns `appState = profiles[name]` as a wholesale replacement. It re-attaches the three transient keys, then runs `sanitizeAppState`, `saveAppState`, `renderGrid`, `updatePrefLayoutUI` and `updateDensityUI`. It does not merge in defaults.
- **Live state:** the working `appState` is saved to `changeout_state_v1`. At startup `loadAppState` deep-merges that over the hard-coded `appState` literal (columns, pills and subdivisions by index), so appState already follows "saved over default" at startup.
- **Export/import:**
  - A single profile exports as `platts-layout-profile`, and the whole set as `platts-layout-vault`; both use `schemaVersion: 1`.
  - Import rejects anything with `schemaVersion !== 1`, runs `sanitizeAppState`, and strips extra keys (`savedSelectedSystems`, `scratchpads`, `projectDetails`, `page2State`, `smartScopeState`, `customerData`, `proposalData`) beyond the three that save already drops.
- **Device handling:** profiles are device-agnostic, with no desktop/mobile distinction. Anything responsive in them is only plain pixel values such as `universalWidth` and gaps.
- **Other settings stores the profile system does not touch:**
  - `changeout_prop_settings_v1` (Page 2 settings, a shallow `{...defaults, ...stored}` merge plus a schema-versioned header-layout migration).
  - `changeout_user_settings_v1` (the dormant layer described in section 7).
  - Smaller keys: cart mapping v3 (reads and migrates v2), `auditDisplaySettings`, `isLightTheme`, `isForceDesktop`, the proposal destination folder id, and a smart-scope help flag.

## 2. What appState and profiles actually capture
All of this is saved by profiles unless noted:
- **Layout/grid:** `colCount`, `rowCount`, `universalWidth`, `universalHeight`, `colGap`, `rowGap`, `indicatorStripHeight`, `layoutArrangement`, and `columns[]` with pills and subdivisions (mapping, label, flex weights, font sizes, alignments, label positions).
- **Density and badges:** `uiDensity`, `siteTagFont`, `siteTagPos`, `showCoastalDiff`, `coastalDiffBadgeScale`.
- **Filters and sort:** `activeFilters`, `resultSort`, `resultLimit`. These three are excluded from profiles. `hideFiltered` is not excluded.
- **Editor cursor:** `selectedColIndex`, `activePillIndex`, `activeSubIndex`. These ride along in profiles even though they are transient.
- **Collapse state:** `isHeaderExpanded`, the page-1 header `<details>` open state. It is the only collapse flag in appState, and it also rides along in profiles.
- **Not present in appState:** modal positions, sizes or collapsed state, device/mobile preferences, and anything about proposals or the Builder.

## 3. What is not currently captured

- **Config export:** the Shift+double-click on the version badge exports `platts-proposal-config` with page-1 layout, Page 2 settings, user-settings overrides and diffs. There is no importer for it.

## 5. Best existing pattern to reuse
The "work modal" pattern, exemplified by `site-setup-modal`:
- a full-screen wrapper with `pointer-events-none`, so the page behind stays usable
- an inner panel with `pointer-events-auto`
- a header with `cursor-move touch-none select-none`
- a button cluster that stops pointer propagation, holding a size toggle and Close

It is driven by two shared helpers:
- **`window.initDraggableModal(panelId, headerId)`** has 12 call sites. It is idempotent, uses pointer events with capture (mouse, touch and pen), clamps to the viewport while dragging (the header can't leave the screen), and re-clamps on window resize.
- **`window.toggleWorkModalSize(panelId, iconSel, expandedClass, compactClass)`** flips the `dvh` height classes and re-clamps `top`.

Weaknesses:
- Nothing is saved.
- Clamping happens only on drag and resize, not when a panel opens.
- There is no true header-only collapse and no resize handle.
- `makeElementDraggable` (an older, unclamped mouse/touch version) has no callers and is dead code.
- The only persisted collapse examples are `isHeaderExpanded` and the Page 2 `defaultExpanded` flags.

## 6. Mobile and desktop implications
- **No JS device detection.** The code uses Tailwind breakpoints (`sm:` 101 times, `md:` 16, no `lg:`/`xl:`), no CSS `@media`, `dvh` units, and `visualViewport` in the drag/clamp code.
- **Force Desktop:** a manual toggle forces the grid to at least 1200 px wide.
- **Pixel coordinates are unsafe across devices.** After a drag a panel holds absolute pixel `left`/`top`. A position saved on a 1400 px desktop would be off-screen on a 390 px phone, and the next drag or resize is the only thing that pulls it back.
- **Recommendation:** save positions normalized (fractions of the viewport, or an offset from the default centered position) and clamp on apply. Use two coarse buckets matching the existing `sm` breakpoint (compact below 640 px, regular otherwise), not orientation-specific buckets.
- **Existing support:** the dormant settings layer already has `desktopMobileLinked` and `{desktop, mobile}` variants for one setting, so the concept is already in the codebase.

## 7. Recommended storage architecture for modal and UI preferences
- **Where to store:** a `modals` section in the existing user-settings layer, not appState and not profiles.
  - Add it to `window.DEFAULT_USER_SETTINGS` and read and write it with `getUserSetting(path)` and `setLocalUserSetting(path, value)`.
  - These keys already provide the precedence you want. `getUserSetting` returns the saved override, otherwise the built-in default. `setLocalUserSetting` stores sparse overrides and drops one if it equals the default. Reset helpers and a `changeout_user_settings_v1` key exist, and the config export already includes the overrides and diffs.
  - A suggested shape is `modals.<modalId>.<compact|regular>.{x, y, collapsed}`, with fractions for x and y.
- **Why not appState:**
  - It is cart and grid data.
  - A profile load replaces it wholesale and would overwrite modal positions.
  - Exporting a profile would carry device-specific positions to another device.
- **Why not profiles yet:** you will likely want modal placement to survive a profile switch. An opt-in "include UI preferences" snapshot can come later.
- **Caveats on the foundation:**
  - It has no consumers anywhere in the file, so it has never carried real data.
  - `loadUserSettingsState` accepts any stored value without validation, so apply code must validate and clamp.
  - There is no migration hook; add a per-section schema number later if needed.
  - Its `smartScope` and `sorter` defaults are unused stubs; the real sorter data lives under `changeout_cart_mapping_v3`.
- **Promotion workflow:** the sparse overrides plus the existing config export and diff mode already show exactly which values differ from the built-in defaults, so the developer promotes them by pasting into `DEFAULT_USER_SETTINGS`. Users can still override later.
- **Keep diagnostics data separate:** a diagnostic log of Create attempts is data, not preferences. Give it its own small key rather than piling it into settings.

## 8. Old-profile compatibility
- **Outside the profile vault:** keeping modal prefs outside `changeout_profiles_v1` changes nothing there. Old profiles and exports load as before and the schema stays at 1.
- **Adding fields to appState or profiles would be risky:** a profile load replaces appState without merging defaults, so a missing new field becomes `undefined`. Each use would need its own fallback, or the loader would need a default merge like `loadAppState` has.
- **Schema bump hazard:** import rejects any `schemaVersion` other than 1, so bumping profile exports would make a newer export unreadable by this build, and the reverse.
- **User-settings layer:** a new `modals` section is additive. Stored overrides without it fall back to defaults, and the loader keeps unknown keys, so older and newer builds tolerate each other.
- **Other risks to design around:** stale coordinates, off-screen panels, duplicated drag logic, one-off localStorage keys, a bloated settings object, and tying settings to transient app state. Saving only on drag end or toggle, clamping on apply, and reusing the existing helper avoid most of these.

## 9. Recommended pilot modal
**The Load Proposal modal.**
- **Why it fits:** it already has a header and a scrolling body, the same split the work-modal pattern expects.
- **Risk:** the modal itself writes nothing, because Load validates before applying.
- **Benefit:** you would most want to move or compact it to see the Builder while reviewing, and it exercises everything: drag, compact toggle, saved position, clamping and mobile.
- **Second:** the Update confirmation modal, which has no header bar and guards a revision write.
- **Third:** the diagnostic card. It does not exist yet, so build it on the shared helper from the start rather than retrofitting it.
- **Open design decision:** work modals use a click-through wrapper, while Load and Update currently block the page with a backdrop. For these two I'd keep the backdrop and make only the panel movable.
