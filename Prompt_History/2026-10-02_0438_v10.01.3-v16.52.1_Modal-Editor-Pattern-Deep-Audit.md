## 2. Page 1 selected-object editor findings
- **Entry point:** every mapped cell and header cell has an always-visible "micro-indicator" strip along its bottom edge (`absolute bottom-0`, height set by `appState.indicatorStripHeight`, default 6 px, range 2–20 px, tooltip "Configure segment"). Its click handler `launchSmartModal(c, pIdx, sIdx)` records the column, pill and subdivision indices and opens `smartModal`. It also syncs the same selection into the Page 1 Settings Inspector.
- **Selection:** `appState.selectedColIndex/activePillIndex/activeSubIndex` plus `dragContext.current*`.
- **No on-grid highlight:** no code in the grid render marks the selected segment. Selection shows only in Inspector button styling and in the modal's Column / Segment / Mapping summary.
- **Live and persisted:** every handler mutates `appState.columns[c].pills[p].subdivisions[s]`, then runs `saveAppState()` (to `changeout_state_v1`) and `renderGrid()` at once.
- **Controls are static markup**, with values refreshed by `updateSmartModalFields()`:
  - **LAYOUT tab:** pill count and split count; column width offset ±5 px (−400…250); split flex weight ±0.1; pill height weight ±0.1.
  - **MAPPING tab:** a grid of all 19 database fields.
  - **ALIGN & FONT tab:**
    - header, data and inline-label horizontal and vertical alignment (3 segmented controls each);
    - label, data and inline-label font sizes ±1 and ±5 (4–72);
    - custom label text;
    - label position (inherit, stacked, inline-left, inline-right, hidden).
- **Scope of edits:** it edits only the selected target, except column width offset and the normalization of splits when counts change.
- **Not supported:** icon size, x/y nudges, per-cell padding. No hold-to-repeat, no arrow keys, no sliders (the old slider handlers `handleModalFlex` and `handleModalOffset` are dead).
- **Duplication:** the Inspector tab edits the same data through different functions with different limits. Flex weight is 0.1 with no upper limit in the modal versus 0.5–5 in the Inspector, and pill height is 0.1 versus 0.5–4.
- **Mobile:** the always-visible strip is touch-friendly and user-adjustable. The header column-width ± buttons appear on hover only.
- **Why the pattern is good:** the edit access is on the thing being edited, the panel is non-blocking, every tap re-renders live, the three alignment groups are one tab of segmented controls, and the summary names the target.
- **Why it is weaker:** no visible highlight on the page, and duplicated handlers.

## 5. Sorter settings findings
- **Shell:** `sorter-settings-modal` is draggable with a compact toggle, `w-[92vw] md:w-80`, centered by translate, `z-index:100`, no backdrop.
- **Why it behaves differently:** it was built as a list manager. `renderCartConfigurator()` builds one string of HTML for the whole layout, with no selection state.
- **How much it shows at once:** the default layout has 3 containers, 7 stacks and 7 splits. Each split shows 4 controls (mapping with 23 options, align, width weight, font). Containers and stacks add weight controls plus remove, move and add buttons. That is roughly 60 controls before master row height and end-cap, plus composite-description sub-controls when used.
- **No selection and no highlighting.**
- **Live behavior:** edits change a template that every cart row uses, so the cart re-renders live.
- **Is the manager paradigm necessary?** Not for editing properties. The data model is the same container → stack → split model as the shared grid and the other grid editors, with width and height weights, mapping, alignment and font. It is needed only for structural administration: add, remove and reorder. A selected-object conversion is feasible by tapping a rendered cart row element, which would need data attributes on the rendered cells.
- **What would be improved:** far fewer controls visible, an on-canvas highlight, and consistency with the shared grid editor.
- **What would be lost, unless kept:** the overview and the reorder buttons, and composite-field editing would need a home. A slim structure outline for add, remove and move would cover the first two, and composite editing fits naturally on a selected split.
- **Recommendation:** do not convert for the sake of scrolling alone. If converted, use a hybrid: selected-object properties plus a compact structure outline.

- **Best compact toggle:** `toggleWorkModalSize`, but it only changes height, not a true collapse.
- **Best confirmation pattern:** the `site-clear-warning-overlay` card (icon, severity header band, short body, two actions).
- **Best manager/list:** none yet; the Sorter is the only large one and it is the weakest at finding items.

## 10. What should be standardized
- **Draggable header:** reuse `initDraggableModal`, extended with an optional drag-end callback.
- **Compact and expanded toggle:** collapse the three state mechanisms into one.
- **Close and control cluster:** one header layout with icons for compact, reset position and close.
- **Viewport clamp on open**, not only on drag and resize.
- **Saved position and state** through one persistence hook.
- **Selected-item highlight and a context card.**
- **A numeric stepper:** the minus / value / plus row with min, max and step, already hand-copied hundreds of times.
- **Z-index scale and default widths.**

## 11. What should remain different
- **Content layout per editor type:** Page 1's tabbed segment editor, the shared grid's one-scroll hierarchy and the Dispatch accordion fit their jobs.
- **Blocking confirmations stay centered** with a backdrop and no drag, because they guard consequential actions.
- **The Sorter's structure operations** (add, remove, reorder) need a list or outline even if properties become selected-object.
- **Read-only viewers** (code, summary, voice help, breakdown) stay simple.
- **The toast stays minimal.**

## 12. Proposed Platts panel types
- **A, Work Panel:** shell only (draggable, compact, click-through).
- **B, Selected-Object Editor:** A plus a selection context card, an on-canvas highlight and steppers. Members: Page 1 segment editor and Inspector, the shared grid editor, Smart Scope item config, header filter.
- **C, Manager Panel:** A plus a list and structure operations (Sorter, audit settings, checklist and settings drawers).
- **D, Blocking Confirmation:** centered, backdrop, no drag (Update, protection resolution, site-clear warning).
- **E, Status or Diagnostic Card:** does not exist yet; the toast is too short-lived and `proposal-export-status` is inline text.
- **F, Info or Reference:** worth keeping as a sixth type; the viewers (code, summary, voice help, breakdown, system details) are read-only and can be either blocking or work panels.

## 13. Mobile and desktop implications
- **Sizing:** most panels are `w-[92vw] max-w-sm|md` (about 360 px on a phone), so they fit. `smartModal` and `headerFilterModal` start at fixed pixel positions (only `smartModal` re-centers itself on open). The Dispatch panel width setting is in pixels.
- **Default placement overlaps the target:** the 10% top anchor covers the Page 2 header and the Page 1 grid while you edit them.
- **Compact mode helps only partly:** it reduces to roughly 32–42 dvh, which still covers a lot of a phone. A header-only collapse (about 48 px) would be the real "move out of the way".
- **Dragging offscreen:** the clamp keeps 100 px of the header reachable, so a panel can be mostly offscreen but recoverable.
- **Touch targets:** the shared grid steppers are 24 px, Page 1 steppers 28–32 px, and Sorter buttons about 20 px, all below a comfortable 44 px.
- **Hover-only controls:** the header column-width ± buttons need hover and are unusable on touch.
- **Background interaction:** practical for work panels because there is no backdrop, but only `site-setup-modal` explicitly keeps the page click-through.
- **Smallest responsive rules:**
  - 40 px or larger stepper targets;
  - a header-only collapse state;
  - clamp on open;
  - on phones, dock the panel to the bottom with a height of at most about 45 dvh so the page above stays visible;
  - two coarse position buckets at the existing `sm` breakpoint (below 640 px and above).

## 15. Recommended future panel standard
- **Shell contract:**
  - A panel has an id, a mode (`work` click-through by default, `blocking` opt-in), default anchor and size, and a header with grip, title, compact/collapse, reset position and close.
  - States: expanded, compact, collapsed (header only).
  - Drag via the extended `initDraggableModal`; clamp on open and resize.
- **Selected-object behavior:** a context card naming the target, an on-canvas highlight (reuse the shared grid's three-level outline), and steppers that edit only that target, with an optional 1/2/5 step selector as the old nudge pad had.
- **Mobile:** larger steppers, bottom dock option, and the bucket rule above.
- **Persistence:** store position and state as sparse overrides under a `modals.<id>.<compact|regular>` section of the dormant user-settings layer (`getUserSetting`, `setLocalUserSetting`, `changeout_user_settings_v1`). That gives saved-override-else-default precedence, resets, and the existing config export and diff for promoting values to defaults. Save only on drag end and toggle.
- **Load Proposal modal, later:** keep its blocking backdrop (Load replaces the cart), add the standard header with drag and compact so the Builder can be seen, keep its list and confirm panels exactly as they are, and make backdrop-blocking a per-panel option.
