## Final Agent Report — Verbatim

The current structure can evolve toward the brainstorm incrementally, but not as one universal model. The app has two real families of grids, and a shared editor layer is realistic where a shared data model is not. I changed no frontend, backend, proposal or rules files, and I made no commit, push or deploy. This was a static read of `retest.html`, with searches and counts, and no browser run; behavior I infer from code is labeled as such. The brainstorm record, `TODO.md` and the two prior audits were read first, and the structural claims below were re-checked against current source.

## 1. Executive conclusion
- **Two grid families, not four copies.** The Page 2 Header and the Dispatch header already share one renderer, one editor, one selection state and one split schema (`renderSharedGrid`, `sharedGridState`). Page 1 and the Sorter are a different kind of grid: a template repeated for every data row.
- **Page 1 is not simply container / stack / split.** Orientation and nesting match, but sizing, mapping, selection persistence and the label/value text model all differ. Unifying the data models would be dangerous.
- **A shared editor layer is realistic.** Selection and highlight, a context card, steppers, the panel shell and a component registry can sit over surface-specific models.
- **Most of the brainstorm's primitives already exist in rough form:** a clone-based component bank and two partial registries, a `<details>` whose `<summary>` holds a grid (Dispatch), and schema-versioned layout sanitizers.
- **Recommended direction:** surface-specific models plus shared editor primitives, with a thin adapter only where needed.
- **Recommended pilot:** an explicit Editor Mode on the two existing shared-grid surfaces. The Proposal Builder action bar becomes the first new surface after that.

## 2. Current structural model map

## 3. Page 1 vs Page 2 / Dispatch / Sorter hierarchy comparison

## 4. Is a common grid core realistic?
For a shared **editor and selection layer**, yes. For one **canonical data model**, not yet. The two shared-grid surfaces already prove a shared core works when schemas match. Folding Page 1 or the Sorter into the same model would need migrations of `changeout_state_v1`, profiles and `changeout_cart_mapping_v3`, for little gain.

## 5. Recommended common architecture strategy

|---|---|---|---|---|---|
| A. One canonical model | High | breaks or migrates every store | highest | everything | no |
| B. Shared helper layer | Medium | none | low | moderate | yes |

## 6. Editor Mode feasibility
- **Wiring today:** about 526 inline `onclick` attributes, 28 `.onclick` assignments, 6 `addEventListener('click')` calls and one delegated document click listener (it only closes inline menus). There are 81 inline `onchange`/`oninput` handlers and only 3 pointer, mouse and touch listeners (the drag helpers).
- **Central interception is feasible.** A single capture-phase `click` listener on `window` that calls `preventDefault` and `stopPropagation` would stop inline, property and listener handlers alike.
- **Gaps in that approach:** `<summary>` toggles are a default action, so they need `preventDefault`. Selects, checkboxes and text inputs act on `change` and `input`, not `click`. Draggable cart rows use `dragstart`.
- **Action suppression today is uneven.** The Page 2 header sets `pointer-events: none` on cloned sources in edit mode. The Dispatch branch builds live handlers (Take Photo, Choose Photo, Extract, gear) with no suppression, so by code reading they run their action while editing. This is not run in a browser and is tracked as a TODO.
- **Highlight is not reusable as is.** It is baked into the `renderSharedGrid` re-render and tied to the settings modal being visible. Page 1 has no on-grid highlight at all. A reusable version should be a CSS class driven by a data attribute, not a re-render.
- **Registration by data attributes is practical.** The only precedents are `data-dispatch-container/stack/split` and `data-page2-site-badge`. Render functions can emit inert `data-` attributes without behavior change: Page 1 uses `createElement` (easy), and the shared renderer builds HTML strings (easy).
- **Nested targets:** resolve with `closest('[data-editor-id]')`.

## 7. Component registry feasibility
- **Existing pieces:** `page2HeaderExternalMappingRegistry` (10 entries with label, type and either a source id or a selector), `dispatchExternalMappingRegistry` (5 entries with label and icon or type, where the action is a hard-coded switch), mapping option lists hard-coded in the editor, and the hidden `page2-header-native-source-bank` of real nodes. `SMART_SCOPE_ITEM_DEFS` is a separate domain.
- **No central action table.** Actions are global functions named in inline `onclick` text (`window.createProposalExportFromRetest()`, `openDispatchCamera()` and similar).
- **Duplicate buttons calling one action already happen.** Dispatch Take Photo, Choose Photo and Extract are created as `…-clone` ids that call the same globals.
- **Instance versus identity is already separated** in the shared grid: visual settings live on the cell (`fontSize`, `iconSize`, offsets) while `mapping` is a string identity.
- **Smallest useful registry:** one flat table per surface family that merges the two registries and the hard-coded lists. Each entry holds `componentId`, `label`, `origin`, `kind` (field, control, display), `source` (clone selector or render callback), `action` (a global function name), `duplicateAllowed`, `requires` (a runtime condition name) and an editor placeholder note. Visual defaults and responsive variants can wait.

## 8. Mapping / Contents architecture recommendation
- **Today** mapping values are plain strings everywhere, with a second field pair (`externalSourceSection`, `externalSourceElement`) for cross-section references.
- **Recommendation:** one user-facing picker with categories (This Section, Other Sections, Global), backed by separate internal types and unchanged storage. Use namespaced ids (`field:`, `control:`, `ext:`) as a view-layer convention only.
- **Migration:** none for existing values. The renderer already normalizes aliases (`mic` becomes `microphone`), which is the precedent for keeping legacy strings valid.
- **Duplicates:** cell address (surface, container, stack, split) is the instance id, and the mapping string is the component id.

## 9. Responsive variant recommendation
- **Today:** no JS device detection and no CSS `@media`; Tailwind `sm:` is used 101 times and `md:` 16 times. There is a Force Desktop toggle. Page 1 has a single set of dimensions, and the shared grids have no breakpoints. The old Page 2 header `desktopLayout`/`mobileLayout` keys are legacy.
- **Key fact:** localStorage is per browser, so your phone and desktop already hold separate overrides. Variants matter for shipped defaults and for resizing or rotating one device.
- **Recommendation (C):** one base layout plus sparse compact overrides for numeric and visual values (sizes, fonts, icons, expanded defaults), stored in `changeout_user_settings_v1`.
- **Structural variants** (a different placement per viewport) cannot be expressed as sparse numbers. Allow a full alternate layout per surface only if a real need appears.
- **Breakpoint:** align one `compact` class to the existing `sm` boundary (640 px).

## 10. Section-level expandable region feasibility
- **Native precedents:** the Dispatch section is a `<details>` whose `<summary>` contains the shared grid, so "persistent bar as a grid plus an expandable body" already exists. Page 1's header is a `<details>` with `appState.isHeaderExpanded` saved. Sorter and Final Output summaries hold ad hoc controls.
- **Suggested representation:** a `region` object holding `id`, `placement` (above or below), `defaultExpanded`, a `bar` layout and a `body` layout.
- **Storage:** a new schema-versioned object in `propSettings` with a sanitizer, following the `page2Header` and `dispatchPanel` pattern.
- **Alert badge when collapsed:** easy, because the bar renders independently of the body.
- **Layout:** collapse changes outer height naturally through document flow, and multiple regions stack in DOM order. The one conflict is `position: sticky` (Page 1's header is sticky), so only one region can be sticky.
- **Rollout:** regions can be inserted per section one at a time.

## 11. Container-level expand-to-fill feasibility
- **Current math:** stacks are `flex: weight 1 0%` (or a pixel lock), the container is a column flex with `gap: stackGap` inside a fixed `headerHeight`.
- **Summing weights is not exact.** Hiding stacks also removes their gaps, which adds free space that every remaining stack shares, not just the anchor. Locked-pixel stacks in the group do not scale with weights. Exact preservation needs gap and pixel compensation (for example a flex basis or margin on the anchor).
- **Persisted state:** keep the stack weights untouched and hide with a display flag, so restoring the expanded state is exact. Compute the anchor's effective size at render time rather than saving it.
- **Stack identity:** stacks have no ids, so insertions or removals shift positions. A group needs stable stack ids or range maintenance.
- **Hidden stacks keep mappings and settings.** Their components are not rendered while hidden, so runtime-updating components must re-render on expand.
- **Multiple non-overlapping groups per container are feasible.** Prohibit nesting at first.
- **The contiguous-only constraint is sufficient** and is also required for the geometry.

## 12. Status/message region findings
- **Where:** the status span, link pair, destination select, Load, Update, Create and the loaded-proposal indicator sit in one flex-wrap row inside the Final Output `<summary>`. Update, links, status and indicator start `hidden` and are shown by toggling.
- **Why messages shift neighbors:** the status span is the first flex item with no width cap beyond `max-w-full` and it wraps. A long message (the recovery texts run 150–250 characters) forces the other items onto new lines, and the summary grows. Adding the links, the Update button and the indicator causes the same wrapping.
- **A designated slot would prevent it:** a reserved row or a fixed-size slot with wrap or scroll.
- **Later mapping:** the slot could become a grid component (a status type with title, message, detail and severity). A grid cell has a fixed height, so long text needs an overflow rule.

## 13. Conditional placeholder findings
- **Conditions today:** Update and the indicator are shown by `updateLoadedProposalIndicator` when a proposal is loaded. The links are shown by the Create and Load code, and the status span by `showProposalExportStatus`.
- **Hidden nodes remain in the DOM** (the `hidden` class), so Editor Mode can reveal them.
- **Safe pattern:** an Editor Mode CSS rule such as `body.editor-mode .editor-conditional { display: … !important }` with a dashed outline, reduced opacity and a "Hidden in current runtime state" label. Do not remove the `hidden` class, because runtime code re-toggles it.
- **Placeholders must not run runtime code,** so give them no handlers.
- **Gap today:** a cloned component that is hidden when the grid renders (for example the site badge) shows as an invisible cell in edit mode.

## 14. Duplicate component-instance risks
- **Id-based single-node assumptions:**
  - `btn-create-proposal` (busy and label state), `proposal-export-status` (text and class), `proposal-links-container` with `proposal-doc-link` and `proposal-pdf-link` (hrefs), `proposal-destination-folder` (value), and `dispatch-image-status`, whose id is reused by the generated cell.
  - The loaded indicator, its title, and Update and Load are looked up once and held in closures. `updateButton` is captured when the page loads.
- **Clones copy inline `onclick` attributes but not `addEventListener` listeners.** Create, Load and Update use inline `onclick`, so the action would run from a clone.
- **State does not follow clones.** Busy or disabled state is applied to the original node, so a clone is not disabled (a double Create is possible), and visibility toggles update only the original. Clones snapshot state when rendered and need a re-render or a live binding.
- **Safer existing patterns:** clone ids are suffixed (`-clone`), the logo clone clears its id, and the site badge is updated through a `data-page2-site-badge` selector across all instances.
- **Recommendation:** keep three ids separate: the component id (what it is), the action id (what it does) and the instance id (the cell address). Centralize busy state in the action, not on a node.

## 15. Label/value/content model recommendation
- **Field** (Page 1 subdivision, Sorter field): label, value and inline label with separate font and alignment (`labelFontSize`, `dataFontSize`, `inlineLabelFontSize`, `headerAlign`, `dataAlign` and the inline pair) plus `labelPosition`.
- **Control** (buttons): text, icon and shell size (`controlSize`, `iconSize`, `fontSize`; Dispatch button properties are a separate set).
- **Text or status:** custom text, title, status text.
- **Recommendation:** a type-aware inspector with a small property list per type (field, control, text/status, media), mapped onto the existing property names, so no storage is renamed. A status card adds title, message and detail roles when it is built.

## 16. Fine-tuning code and UX reuse findings
- **Reusable code, with adaptation:** the shared-grid schema already holds `offsetX/offsetY`, `widthLocked/lockedWidthPx`, `heightLocked/lockedHeightPx`, `wrapMode`, `overflowMode` and `controlSize`, and both renderers apply them. The shared editor offers no controls for them. The legacy `nudgeDispatch`, `setDispatchLock/Px`, `modDispatchSplitNum`, `moveDispatchMapping/Stack/Split/Container` and the 21 legacy Page 2 header functions are tied to old selection variables (`dispatchSelected*`, `page2HeaderSelected*`) but edit the same data, so rewiring them to `sharedGridState` is small.
- **Reusable UX ideas:** the nudge pad with a 1/2/5 px step selector and a center reset, lock toggles with a pixel entry, accordion sections with per-section default open state, and the selected-cell context card.
- **Dead or unusable:** `handleModalFlex`, `handleModalOffset`, `stepColGap`, `stepFlexWeight`, the Page 2 header global keys (`logoHeight`, `titleFontSize`, and similar, now used only to seed the canonical layout and by Diff Mode), and the unreachable legacy tabs themselves.

## 19. Recommended pilot
**Editor Mode on the two existing shared-grid surfaces (Page 2 Header and Dispatch).**
- **Why:** no new storage and no backend change; one renderer and one schema; both surfaces already have selection and a context card. It exercises the new concepts in a bounded area: an explicit toggle, data-attribute targets, a central interceptor, action suppression (which also fixes the Dispatch gap), and hidden-component placeholders.
- **Validation:** desktop and phone widths with the existing mock browser suite.
- **Immediate follow-on:** the Proposal Builder action and status bar as the first new surface. It carries more risk because it touches the just-stabilized Create, Update and Load flows.
- **Not the pilot:** the Load Proposal modal, the Sorter conversion (it needs an on-canvas preview first), and Page 1 (the largest model).

## 20. Things NOT to implement yet
- A universal component registry across the whole app.
- Migrating Page 1 or the Sorter to the shared-grid schema.
- Restoring every dormant legacy control as it was.
- Cross-section mapping everywhere.
- Nested or non-contiguous expandable groups.
- Full duplicate desktop and mobile layouts.
- Making arbitrary DOM nodes editable.
- Deleting the legacy editors before a decision.
