## 1. Executive conclusion
- **Go.** The Proposal Builder bar is a good first new surface. It has a visible mobile problem, no existing grid model, and a small, well-bounded set of controls.

## 4. Exact causes of the desktop and mobile problems
- **Common cause:** one `flex-wrap` block holds both fixed items and items that appear later (status text, DOC/PDF, Update, the 256 px loaded box). Anything inserted ahead of Load on its row pushes the rest along or onto a new row, and the wrap points change with the state.
- **Desktop:** the block is right-aligned, so items inserted on the left slide the buttons left (Load −93 px). The loaded box (256 × 73 px) is too tall for the row, so Copy Text and the gear drop to a second row. The title is centered against a bar that grows from 55 to 141 px, so it drifts.
- **Portrait:** the title takes about 90 of 411 px, leaving about 250–280 px. The 192 px select leaves no room beside it. Load and Create fit together (about 190 px). Adding Update makes them 264 px, so Create wraps alone. The status text sits above everything and can reach five lines.
- **Landscape:** all items share one wide row until it saturates. Inserting status and links pushes Load right by 218 px and wraps Create to the next row. Where the utility controls land depends on font and width.
- **Deliberate or natural?** Natural wrapping. The exact wrap points even differ between your phone and my render at the same viewport class.
- **The summary height grows** in every orientation (about 2× in portrait), and the title, Copy Text and gear shift independently.

## 5. Recommended grid grouping
- **Keep the title outside the grid,** as the summary's first child, so it can sit on top in portrait and on the left otherwise.
- **Four groups, in one grid inside the summary:**
  - **Actions:** destination, Load, Update slot, Create.
  - **Result:** status slot, DOC and PDF slots.
  - **Utility:** Copy Text, gear, collapse hint.
  - **Loaded indicator:** its own last row (see rule in section 14).
- **Keep the preset/note strip outside** (section 16).
- **Why one grid and not two:** the utility controls and the status must stay in the persistent summary so they remain visible when the section is collapsed, as they are today.

| Selection, highlight, context card | B | belong to the later editor phase |
| Edit-mode placeholder | C | only an "empty" placeholder exists |
| Layout sanitizers and schema versions | C | the pattern is good (page2Header schema 1, dispatchPanel schema 4); a new sanitizer is needed |
| Persistence | A (pattern) | a `propSettings` sub-object saved by `savePropSettings()` |

## 7. Original node versus clone recommendation
**Option A: physically move the original nodes into slots.** Never clone stateful controls.
- **Busy state lives on one node.** Create sets `disabled` and "Creating…" on `#btn-create-proposal`, Update disables the cached `updateButton`, Load disables itself. A clone would not be disabled, which allows a double Create.
- **Hrefs and visibility** are written to single nodes by id, so clones would go stale or unsynchronized.
- **Ids must stay unique,** and `updateButton` is captured by identity.
- **Cloning is acceptable only for pure displays** such as a logo. Clone-safe types come later with the registry.
- **Option C** (new instances bound to shared action and state) is the right long-term answer for duplicates, but it needs centralized busy and visibility state first. **Option D** (placeholders around the originals) is the same as moving the originals into slots.

## 8. Minimum grid schema
Phase 1 needs only structure and width behavior:
- **Surface:** `schemaVersion`.
- **Containers:** one, with `stacks[]`.
- **Stack (a row):** `splits[]`, optional `minHeightPx`; height is auto, not fixed.
- **Split (a slot):** `mapping` (a component id), `widthMode` (`auto`, `weight` or `px`) with `widthWeight` or `lockedWidthPx`, and `horizontalAlign`.

Left out for Phase 1: font size, icon size, offsets, locks, nested grids, responsive variants and component metadata. Original nodes keep their own styling. Slot behavior such as "reserve when hidden" belongs to the component definition in code, not to stored data.

## 9. Storage and schema recommendation
- **Location:** `propSettings.proposalBar`, a new top-level object, following `page2Header` and `dispatchPanel`.
- **Why:** it is layout, not proposal data, so not the Builder State or manifest; it is not Page 1, so not `appState` or profiles; and the config export already includes `propSettings`.
- **Compatibility:** `propSettings` loads with `{...defaults, ...stored}`, so an old store without the key keeps the default, and an older build ignores the extra key.
- **Schema strategy:** `schemaVersion: 1`, a default layout constant, and `sanitizeProposalBarSettings()`.
  - It fills defaults.
  - It accepts only known mapping ids and a mapped component at most once (stateful controls are singletons).
  - It falls back to the default layout on any invalid shape.
- **Writes:** Phase 1 reads stored overrides but does not write them. The editor phase writes.
- **Later:** user-level sparse overrides can come from `changeout_user_settings_v1`.

## 10. Responsive strategy
**Same structure, different widths** (option A) is sufficient here, with a small set of compact rules expressed in CSS at the existing `sm` breakpoint (640 px).
- **Evidence:** the same controls appear in portrait and landscape. The portrait problem is the title consuming width and the 192 px select sharing a row with the buttons.
- **Compact rules:** title on its own row on top; the destination cell takes a full row; the three buttons share the next row; utility controls on their own row.
- **Structural variants are not needed** because the reserved slots make the wrap points depend only on width. A full alternate layout would only be justified if a later design wants a different arrangement per viewport.
- **Narrow phones:** on a 360 px phone the three buttons (about 264 px) may not fit; Create would then wrap in a fixed, predictable place.

## 11. Status/message region recommendation
- **One transient status slot** for all writers of `showProposalExportStatus`: "Proposal created", "Loaded … · Rev N", "Updated … · Rev N", the connection-lost and recovery text, and validation errors.
- **Keep the loaded-proposal box separate,** because it is persistent.
- **Slot geometry:** reserve the height of one line on desktop and landscape and two lines in portrait, wrap the text, and cap it at about four lines with internal scrolling.
- **Do not change the status node's text.** `clearLoadedLinks` compares `textContent`, so clamping must be done with CSS only.

## 14. Conditional-component geometry rules
- **Principle: growth is append-only.** Anything that appears later grows the bar downward, so the controls above and beside never move.
- **Status:** slot remains (reserved height).
- **DOC / PDF:** slot remains (hidden but occupying width).
- **Update:** slot remains between Load and Create (hidden, inert). The cost is a visible gap before a proposal is loaded; the alternative is to move Update to the end of the row, which changes the button order and is your call.
- **Loaded indicator:** no reserved space; it is the last row, so it only pushes the content below the bar. Keep its text; reducing it to one line is a content decision.
- **Editor Mode placeholders** (later) can show these slots dashed.

## 15. Collapse/details behavior recommendation
- **Keep the whole grid inside the `<summary>`,** so status, the loaded box, Copy Text, the gear and the hint stay visible when collapsed, exactly as now (the render confirms the bar is unchanged when collapsed apart from the hint).
- **Keep `details.group`,** because the hint swaps through `group-open:` CSS.
- **Leave semantics alone:** clicking non-interactive areas still toggles the section, and the select and buttons already work inside the summary.

## 16. Preset/note row recommendation
Leave it alone in Phase 1. It is in the details body, a separate `flex-col sm:flex-row` strip. It contributes to landscape awkwardness (the custom text input shrinks to a sliver) but not to the header problem, and changing it would enlarge the scope. It can be a small separate follow-up.

## 22. Ranked risks
1. **Accidental behavior change to Create, Update or Load.** Mitigation: touch no handler, and verify with the request log and the existing suites.
2. **Conditional-slot geometry:** the visible gap for the Update slot, and blank space from reserved slots.
3. **Status overflow** with long messages, and the `textContent` comparison in `clearLoadedLinks`.
4. **Mobile geometry** on narrow phones and with larger font scaling.
5. **Reparenting the originals** (low: no position-based lookups, and identity is preserved).
6. **Details/summary semantics** (clicks on non-interactive areas toggle the section).
7. **Saved-state compatibility** (low: additive key plus sanitizer).
8. **Cloning stateful controls**, avoided by design.
