   - A band is stacks → splits → mapped component. In code it is viewed as a one-container surface so the existing stack/split rules, sanitizer and editor logic are reused.
   - Capability metadata is still runtime-only and was extended: `allowedSurfaces` now uses `summary`, `actions` and `band`. `region:messages` is band-only and required, `display:loadedProposal` is `actions` + `band`, and the gear stays Summary-only and required.
   - Singleton placement is now enforced across the whole layout, with the first placement in Summary → Actions → bands order winning.

5. **Migration from v10.01.6.** A v10.01.6 (schema 2) layout loads without being rewritten:
   - Summary and Actions are kept exactly (mappings, weights, counts, gear). Actions gets an Auto height.
   - `messagePlacement: above` becomes one band Before Summary; `below` (or none) becomes one band Between Summary and Actions. Each holds the message region, is Always visible and Auto height.
   - Desktop and Mobile migrate independently, so Desktop can end up above and Mobile below.
   - v10.01.4 layouts still migrate, through the same path.
   - The saved data stays as it was until your first editor change, which writes schema 3. An untouched Mobile v10.01.6 entry keeps loading.
   - Tested with both placements.

6. **Overall Actions height control.** The Actions region has an "Overall height" stepper: Auto, or a minimum height. It starts at 120 px from Auto, steps by 20 px up to 1000, and stepping below 60 px returns to Auto. It is a minimum: if the content needs more, the surface grows and nothing is clipped. Desktop and Mobile save independently. Summary stays natural height on purpose, so the collapsed strip stays compact.

7. **Container width ratio behavior.** Unchanged and now explicit: sibling containers divide the surface width by share. Growing one container's weight narrows its siblings relatively and the surface width stays the same. The editor shows each weight with its share (for example "2.0 · 50%"). Weights are never forced to total 100.

8. **Stack height ratio behavior.** With an explicit height (Actions or a band), each stack takes a true share of its container's height: stacks 1/2/1 become 25%/50%/25% minus the gaps, and raising the height grows every stack while keeping the ratio. A stack weight of 0 stays natural height and takes no share. With Auto height there is nothing to divide, so stacks keep natural height and weights only share spare height beside a taller container. The editor says so next to the control, and I kept that behavior so saved layouts look the same as before.

9. **Split width ratio behavior.** Split weights divide the width of their stack. Going from 1/1 to 2/1 makes the first split twice as wide as the second while the stack width is unchanged. This works the same in bands.

10. **One-stack fill behavior.** With an explicit height, a single stack with a normal weight fills the whole container height, so the earlier look of empty space above and below it is gone. Weight 0 still means natural height by design.

11. **Full-width Band model.** A band spans the section and contains stacks → splits → components. Several bands can coexist, positioned Before Summary, Between Summary and Actions, or After Actions. Each has an Auto or minimum height and a collapsed-state policy: Expanded only, or Always visible.
    - Bands Before Summary or Between live in the persistent summary strip. "Expanded only" hides them through CSS when the section is collapsed.
    - Bands After Actions live under the action grid. One set to "Always visible" moves into the summary while the section is collapsed and back under the grid when expanded.
    - Band stacks have no gap between them, so a band whose content is hidden collapses to zero height.
    - The model leaves room for a component to own a contextual band later: bands are plain ordered entries and cells have addresses.

12. **Band editing controls.** In the same panel, a third region button sits beside Summary and Actions: "Editing region: [Summary] [Actions] [Bands]". For Bands it offers:
    - B1/B2… chips, Add band, Remove band.
    - A Band position picker with ↑ Earlier / ↓ Later.
    - A Height stepper (Auto or px) and the collapsed-state toggle.
    - Stack and Split chips, stack count, split count, stack and split weights, alignment, and the Contents picker.
    - Reset Bands.

    Terminology is "Full-width bands", "Band position", "Band 1", Stack, Split and Contents. The old Above/Below title-strip control is removed.

13. **Band ordering/placement.** Position is changed with the picker, and order within a position with ↑ Earlier / ↓ Later. A new band starts Between Summary and Actions, Expanded only, Auto height, empty. At most 6 bands. The built-in default is one band holding the message region.

14. **Dynamic Message Region mapping.** `region:messages` is one mapped original component (`#pb-message-region`, with the original status node inside as the primary banner). It is a required singleton, allowed only in bands. Its Protected component section has Move only, with valid destinations highlighted and an occupied cell swapping places, exactly like the gear.
    - Decision: required, because silently losing a recovery or error message after a failed Create is unsafe.
    - That also means zero bands is not allowed: a saved layout with no band gets a default one, and the last band cannot be removed.
    - Removing a band that holds the region relocates it to the nearest empty cell of another band, or blocks with a reason when no empty cell exists.
    - Stack and split reductions use the same relocate-or-block rule as the gear.

15. **Message preview behavior.** While editing and no real message is showing, the region shows three editor-only sample banners ("Creating proposal…", "Checking saved state…", "Proposal created successfully.") so width, wrapping, height, padding and band placement can be judged. They are plain DOM, not messages: no banner entry, no backend request and no proposal state is touched. They disappear when a real message appears and when the editor closes.

16. **Runtime multi-message behavior.** The keyed banner system is unchanged: ids like `create-progress`, `recovery` and `status`, replace-by-id, independent removal. Verified: 0 messages is a zero-height region, then 1, 2 and 3 banners stack vertically with the region growing each time. A long message wraps and the Auto band grows to exactly the region height. Progress and warning coexist, success replaces progress, and removing one banner leaves the others. A message stays visible with the section collapsed when its band is Always visible.

Hidden at runtime with no proposal loaded, a band holding only it collapses to zero height. Edit mode shows the real component with sample text. Once loaded, the real indicator shows in the band and uses the full band width instead of the 16rem cell cap; on the mobile profile its long text wraps over several lines. Moving it between regions keeps the same node. Reset Bands returns it to its default Actions cell if free, instead of leaving it unplaced.
