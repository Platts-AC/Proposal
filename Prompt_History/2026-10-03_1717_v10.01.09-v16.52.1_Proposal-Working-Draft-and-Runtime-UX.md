5. **Conditional-control runtime model.** An actionable conditional control is in one of three states:
   - **Available:** its normal semantic color, interactive.
   - **Unavailable:** it stays visible in its mapped cell, muted (slate fill, gray text, dashed outline), genuinely disabled (`disabled` for buttons and inputs), `aria-disabled`, inert, out of the tab order, and the cell shows a hover hint. This is component-type aware: actionable controls stay, informational displays may collapse (item 9).

6. **Update.** With nothing loaded it stays in its cell, muted, disabled, with no click action and the hint "Available after loading an existing proposal." After a Create or Load it turns amber and opens its confirmation dialog as before (tested with a real click). Its own busy-disable during a save is untouched.

7. **DOC.** Unavailable (muted, inert, `aria-disabled`, hint) when the links container is hidden or the anchor has no `https` href. A stale href cannot be followed: real clicks never reach it, and a programmatic click is cancelled at capture before it can navigate. Available (blue, active href) after Create or Load. If a proposal has a document but no PDF, only PDF stays muted.

8. **PDF.** The same rules, rose when available, hint "Available after a PDF is generated." Both links keep their cells in every state; the existing URL synchronization is unchanged.

10. **Collapse/expand anchoring implementation.** When you tap the Summary, a capture-phase handler records its viewport Y before the browser toggles the section. After the `toggle` event the engine measures the Summary again and corrects the scroll by the difference. It does that immediately, in the same task (so no jumped frame is painted), and again after two animation frames to confirm. Browser scroll anchoring is switched off on the scroller during the toggle (so it cannot fight the correction) and restored afterwards. Only a real tap or key press on the Summary does this; programmatic open/close (the editor's, for example) does not.

11. **Bottom-of-page compensation strategy.** The measured cause: the section is the last thing on the page, so collapsing shortens the document below the scroll position and the browser clamps the scroll, dragging the Summary down (in v10.01.8: 279 px mid-page and 520 px at the bottom). Before the section collapses, a bottom reserve is added as padding on the page's scroll content, sized to exactly the room the vanishing body will leave. After layout settles it is trimmed to the blank part the view still shows, and it shrinks as you scroll up. It is gone once you scroll up (it peaked at 520 px of an 800 px viewport on desktop and 675 px of 891 px on a phone) and gone again after an expand, with the original padding restored. It is never larger than the blank space actually showing, and a programmatic collapse adds none.

12. **Working-draft storage key.** `platts_proposal_working_draft_v1` (localStorage). The existing project keys are a mix of `changeout_*_v1` and `plattsProposal…`; I used the namespaced, versioned name suggested in the task.

13. **Exact working-draft contents.** One JSON object: `schemaVersion` 1, `appVersion`, `savedAt`, `selectedProposalRows` (numeric and string ids exactly as they are), `systemScratchpads` (every scratchpad as it is, including custom base prices), `proposalAppState` (which already holds the customer/job data: date, name, address, phone, email, job number, advisor, include-in-copy; also injected lines, text overrides and the active site), `catalogRefs` (one fingerprint per referenced catalog position: AHRI, brand, series, capacity, type, site, stage; not price) and `derivedFrom` (`{baseName, revision}` or null). Not included: the loaded managed proposal, images or any binary, generated HTML, a catalog copy, modal state. The destination folder already persists through its own existing preference (`plattsProposalDestinationFolderId`), so it is not duplicated. A typical draft is a few KB (tested under 30 KB), and anything over 768 KB is refused.

14. **Auto-save triggers.** The app's own central redraw functions are wrapped (`updateProposalCartUI`, `updateProposalTerminal`, `refreshSiteDependentUI`, `updateJobDataFromForm`, `clearJobDataForm`), each scheduling a 0.5 s debounced save, so adding or removing a system, scratchpad edits, typing customer fields and Clear Customer Info all save without one-off patches. A slow 2.5 s backstop poll catches any change that bypasses them, and the draft is also flushed when the page is hidden or unloaded. A write happens only when the draft text actually changed (15 meaningless re-renders wrote nothing), and a blank quote removes the key instead of writing one. Saving stays off until the restore decision is made, so the blank page can never overwrite the stored draft.

15. **Restore timing/validation.** Once, after the equipment catalog has loaded (it polls every 0.2 s, then every 2 s, until then). With no stored draft, saving is armed immediately. Otherwise the draft goes through: schema version check, the existing managed-Load `validateLoadedBuilderState` and `normalizeLoadedProposalAppState`, and the catalog fingerprint check. It is then applied with the same snapshot-and-roll-back pattern as managed Load (modals closed, state replaced, customer fields re-hydrated, cart badge, Sorter, grid and the Proposal output rebuilt), followed by a toast.

16. **Invalid/stale row handling.** An unsafe draft is rejected whole, never half-restored: a console warning, a toast, the stale draft removed, and a blank page. Rejection covers an unreadable draft, a wrong version, selected options without scratchpads, an index outside the catalog, and a catalog position that now holds different equipment (the fingerprint check). An unused scratchpad whose equipment changed is only reported and does not block the restore. I chose whole-draft rejection because options, text overrides and numbering depend on each other, and the task says never to create wrong equipment silently.

17. **Managed-proposal relationship restore policy.** The loaded managed proposal (identity, revision, Update) is never restored. After a refresh the working state comes back as plain working state: nothing is loaded, Update, DOC and PDF are muted, the Loaded box is hidden, and Create works. A refreshed page can therefore never overwrite a server revision. `derivedFrom` only records where the draft came from, and the restore toast says so ("It came from … Rev N: load it again to Update it.").

18. **New Quote clearing behavior.** After the existing New Quote (and the managed-proposal layer's reset) the draft is removed, the draft layer's memory of its source is dropped, and the customer fields are re-synced with the cleared state. That last step is a small behavior change: before, New Quote cleared the state but left the old customer values in the visible inputs, where the next keystroke could bring them back. The blank state is not written again (checked for 3 s), and a refresh stays blank.

19. **Customer clear behavior.** Clear Customer Info is saved like any change. The draft keeps the options but no customer data, and a refresh shows blank customer fields.
