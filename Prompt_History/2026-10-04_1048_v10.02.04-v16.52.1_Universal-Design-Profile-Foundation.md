## Design Profile Schema (v1)

```json
{
  "format": "platts-design-profile",
  "schemaVersion": 1,
  "appVersion": "v10.02.04",
  "profileName": "Office Desktop",
  "targetClass": "desktop",
  "createdAt": "2026-10-04T14:46:50.000Z",
  "updatedAt": "2026-10-04T14:46:50.000Z",
  "notes": "",
  "design": {
    "proposalBuilder": {
      "desktop": { "schemaVersion": 3, "revision": 5, "surfaces": { "summary": {}, "actions": {} }, "bands": [], "styles": {} },
      "mobile": null,
      "editorAppearance": {}
    },
    "page2": {
      "pageWidth": { "mode": "fixed", "fixedWidth": 1500 },
      "header": { "headerHeight": 88, "headerLayoutSchemaVersion": 1, "headerLayout": { "containers": [] } }
    }
  }
}
```

Layout objects are abbreviated above. `null` for a layout means "built-in default". A namespace missing from `design` means the profile does not govern it. Backup files: `{ "format": "platts-design-profile-vault", "schemaVersion": 1, "profiles": [ ... ] }`.

An internal state map classifies every storage key the page uses as design, working, preference or legacy (a test fails if a new literally named storage key appears unclassified; keys held in constants are classified by hand), and capture only ever reads the five registered units, so nothing else can leak in.

9. **Capture architecture.** `window.captureDesignState(targetClass)` walks the registry and asks each unit for its value; the result is the nested `design` object. Reads only (a test proves nothing in storage changes). The class decides what is read: Desktop = Desktop layout + editor appearance + page width + header; Mobile = Mobile layout + editor appearance + header (no Desktop layout, no page width, because a phone ignores the width mode); Mixed = everything. A layout with no saved override is recorded as `null` (built-in).

10. **Apply architecture.** `window.applyDesignState(profile)`: validate the whole profile first (format, schema, per-namespace validation and sanitizing through the editors' own sanitizers), then apply only the namespaces the profile contains, each through the same setter the editor uses (`setLocalUserSetting` / `resetLocalUserSetting` for layouts and editor look, the existing width and header code for Page 2), re-rendering as it goes. It returns what was applied, skipped, ignored and failed. Nothing is written if validation fails.

11. **Registry / extensibility model.** `window.designProfiles.register({ id, title, surface, targets, capture(), validate(raw), apply(value) })`; the id is a dotted path under `design` (for example `page2.header`). Future migrated surfaces register themselves (the later Page 2 header migration can replace `page2.header` with its new shape under the same id) and the save / load / export / import plumbing does not change. Unknown namespaces in a file are ignored safely.

12. **Desktop / Mobile behavior.** Kept as two separate layouts. A profile can hold Desktop, Mobile or both; the class is chosen on Save New and defaults to the current screen (Desktop on a wide screen, Mobile on a phone). Loading a Desktop profile never changes the Mobile layout and the reverse (tested with both orders), and a Mixed profile carries both side by side. Device names such as "Dan Android" or "iPhone Field" are only names; there is no device detection.

13. **Save New.** In the Design Profiles dialog: name + class + Save New. The name is trimmed, single-spaced, plain text, 60 characters at most; a blank name is refused. An existing name (any capitalization) asks before replacing, and a replace keeps the original creation date.

14. **Update.** Re-captures the current design for the profile's own class, after asking; keeps name, creation date and notes and refreshes the update date. Declining changes nothing.

15. **Load.** Applies the selected profile and shows a concise message and toast ("Loaded design profile ... (N sections ...)"). It does not reload the page or touch job state, and sections the profile does not contain are left as they are.

16. **Rename / Delete.** Rename prompts with the old name; a clash with another profile (any capitalization) asks before replacing it, and a blank or unchanged name is refused. Delete asks first and leaves the current design unchanged. Both use the browser's own confirm / prompt boxes, like the Layout Vault.

17. **Export.** One profile downloads as readable, 2-space-indented JSON (not minified, stable field order, trailing newline) named `platts_design_<safe-name>_v10.02.04_<timestamp>.json`; the exported text is the cleaned, validated profile. Backup all downloads every profile in one vault file named `platts_design_vault_v10.02.04_<timestamp>.json`. The browser never rewrites source code: promotion into the built-in defaults stays an IDE step using that file.

18. **Import validation.** The file must be valid JSON of at most 2 MB, an object with `format` `platts-design-profile` (or the backup format) and `schemaVersion` 1, with a `design` object holding at least one understood namespace. Every recognized namespace is validated and sanitized (layouts through the Proposal Builder's own sanitizer, width mode and range, header counts and ranges, editor ranges); the whole file is refused with a message if one is unusable, and nothing is stored. Names, notes, labels and header text are plain data: no HTML is ever parsed or run, `<`, `>` and `"` are removed from header text, and a `__proto__` key cannot pollute anything. A name clash asks before replacing; a backup is validated as a whole (one bad profile refuses it) and asks once about clashing names.

19. **Partial-profile behavior.** A profile may contain any subset of namespaces. Loading it applies only those and leaves the rest exactly as they are: for example a profile with only a Desktop layout leaves Page Width, the Page 2 header, the Mobile layout and the editor appearance untouched (tested). Unknown future namespaces and fields are ignored, listed as "ignored" and not stored.
