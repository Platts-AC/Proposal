## Final Agent Report — Verbatim

**Reconnaissance done: Custom / Standalone proposals fit the current architecture with little plumbing, but two things need a decision first.** The saved Builder State is already opaque JSON that Load preserves, so custom data can ride inside `proposalAppState` with no backend change. The real work is on the output side, which stops early when no system is selected. I also found a pre-existing bug that sends stale proposal text after the last system is removed. Nothing was implemented; only the brainstorm record, the TODO and this handoff record were written.

1. **Current architecture findings.**
   - **What a managed proposal saves.** Create (`retest.html` ~25044) and Update (~26050) clone `{ proposalAppState, systemScratchpads, selectedProposalRows }` and add a `pricingSnapshot`. The backend treats a proposal as managed whenever `builderState` is an object and never reads its contents on Create. It writes `Proposal Data/<proposalId>_manifest.json` (schema 1, with the whole `builderState`) beside `Proposal Docs/` and the PDF.
   - **Update.** It requires the three keys, snapshots the old manifest to `Proposal Data/Archive/<id>_builder_state_v<N>.json`, archives the old Doc and PDF, and then replaces `builderState` wholesale.
   - **Retrieval.** `getProposalState` returns `builderState` untouched. `listManagedProposals` returns only id, name, revision and dates, with no type.
   - **Load.** It validates, normalizes (keeping unknown keys), swaps the state and regenerates everything under the current device's settings.
   - **Recoverable today:** job data, per-system scratchpads, cart order, text overrides, block order, injected lines and a pricing snapshot.
   - **Not recoverable:** the proposal text itself (it lives only in the Doc and PDF), the exact wording and selection marker from the saving device's settings, and the structure of injected lines (stored as finished strings).
   - **Output model.** The output is a list of `{ target, text }` blocks, plus ordering, overrides, injected lines and a boilerplate block. It is reusable for custom items under new target names.
   - **Hard-coded system wording.** The intro sentence is built by system-specific code, and only five headings and closing texts are templated.

2. **Exact blockers and assumptions tied to selected HVAC systems.**
   - **Early returns.** `updateProposalCartUI` (11280) and `updateProposalTerminal` (12599) return early with no rows. The terminal shows a placeholder, injected lines do not render, and `pureCopyText` is not regenerated.
   - **Other row-dependent code.** The intro composer, the Option / Fees / Upgrades / Protection builders, crane and site helpers, quick-summary placement and the draft `isBlank` test all work from the rows. None throws on an empty cart.
   - **Create guard.** The only guard is "Missing Date, Name, Address, or Proposal Output." There is no system check in the frontend Create or the backend (Update only needs the three keys, which `{}` and `[]` satisfy).
   - **Experiment 1: fresh page, no system.** Create is refused locally and no request is sent.
   - **Experiment 2: a system removed, then Create.** The stale 749-character text still contained "System Option 1" and was sent with `selectedProposalRows: []` and an orphaned scratchpad; the mock accepted it as Rev 1. This is a pre-existing hazard in System Changeout.
   - **Experiment 3: injector with no system.** An injector line is stored but never rendered.
   - **Experiment 4: a zero-row state with an extra key inside `proposalAppState`.** It loads, passes validation with one warning, and the extra key is kept.
   - **Experiment 5: the Load pricing panel for such a state.** It says "No pricing changes detected", which is misleading for typed prices.
   - **Experiment 6: draft.** A custom-only state counts as blank, so it would not be saved.
   - **Same-name collision.** The backend refuses a second managed proposal named `<date> - <customer> - Proposal` in a destination folder, so a system and a custom proposal for one customer on one day collide.
   - **Reproduction.** The experiments ran in the mocked harness (no real backend, no real proposal); the scripts are in the session scratch area.

3. **Recommended Custom Proposal state model.**
   - **Where it lives.** `proposalAppState.proposalType` (`'system'` when absent, so old proposals are unchanged) and `proposalAppState.customProposal`. Both travel through Create, Update, the draft and Load with no change to the builder-state literals.
   - **Fields.** `customProposal` holds `schemaVersion`, `intent`, `scopeTerms`, `presentation` (`combined`, `itemized` or `options`), an optional `packageTitle`, and `items`.
   - **Item fields.** Each item has `id`, `genericType`, `action`, `name`, `description`, `brand`, `model`, `price` (null prints none), `role` (`package`, `line` or `option`), `marker` and `catalogRef`.
   - **Design rules.**
     - An item owns its values; a catalog entry only pre-fills it, so saved proposals load on any device.
     - Role is stored per item, so the three owner modes are presets and a later "base package plus options" proposal needs no migration.
     - Both modes' data survive a type switch.
     - Prices are typed numbers; the pricing engine, site profiles and pricing snapshot are never involved.
     - One sanitizer is used on Load and on draft restore.

4. **Recommended UI placement.**
   - **Proposal Type** is a new `control:proposalType` select component in the Actions area, placed by a one-time layout revision migration (the injector band set the precedent). It is optional rather than required, and the Custom panel appears whenever the saved type is Custom, so a layout that hides the control cannot strand a loaded proposal.
   - **Custom builder** is a new collapsible section in the Page 2 body between the customer panel and the Smart Scope checklist. It holds job intent, scope-term chips, the presentation choice and an item-card list, with a paste-friendly description box per item.
   - **Smart Scope and Systems Sorter** are hidden or collapsed in Custom mode.
   - **No universal grid.** The item list is dynamic, so it does not use the grid, but the panel can become a Design Profile surface later.

5. **Recommended output model for Combined / Itemized / Customer Options.**
   - **Reused unchanged:** Customer Information, ordering, the Focus Editor, injected lines and copy.
   - **New blocks with their own targets,** so overrides and the pricing snapshot never collide with System Changeout.
     - `Custom Intro` is composed from intent and scope terms.
     - `Custom Closing` comes from a new template key.
     - Combined Package prints one `Custom Package` block with bullet items and one `Investment: $total`.
     - Itemized prints `Custom Item N` blocks, each with its own `Investment`, plus an optional `Custom Total`.
     - Customer Options prints `Custom Option N` blocks using the existing selection marker setting.
   - **Pipeline seam.** The pipeline needs one change: decide "anything to render" by proposal type instead of row count, and have the empty path reset `pureCopyText`.
   - **Smart Injector boundary.** The Smart Injector keeps notes, customer-responsibility lines, one-off fees, enhancements and spacers: items are state, injector lines are text.

6. **Managed proposal save/load implications.**
   - **No backend schema change** in the first phases. The Update check is already satisfied by `systemScratchpads: {}` and `selectedProposalRows: []`.
   - **Load needs** a custom sanitizer, type-aware validation (no "no selected options" warning for custom), a custom branch in the confirmation panel (items, mode, total, no catalog price comparison) and a custom render after apply.
   - **Draft** needs an `isBlank` extension.
   - **Optional later:** `proposalType` in the manifest and the Load list, and a custom name suffix for the collision.

7. **Device ID / registry findings.**
   - **Device ID.** None exists today. Create `DEV-` plus 10 random hex characters at the first save, store it locally, and never fingerprint the device. The immutable ID travels in events and proposals; name, assigned user, device type and first / last seen live centrally and are attached by an administrator.
   - **Proposal breadcrumb.** A top-level `provenance` block (`createdOn` and `lastSavedOn`: deviceId, appVersion, time) added next to `attachPricingSnapshot` at both save sites. Update replaces the whole `builderState`, so `createdOn` must be carried forward. Load and pricing ignore the extra key (checked).
   - **Backend dispatcher.** `doPost` is an `if` chain, so a new `recordRegistryEvents` batch action (idempotent by event id) fits.
   - **Sheet access.** The script already uses the bound spreadsheet, so no new scope is needed. Locking and `jsonResponse` are reusable, and `Audit_Approval` to `Audit_History` is a ready model for review and history. `Static_Enhancements` delivered through `doGet` is the precedent for approved shared entries.
   - **To add:** the action, validation and size caps, formula-safe cell writes (text starting with `=`, `+`, `-` or `@`), one-time tab setup and a web-app redeploy.
   - **Existing risk.** The endpoint is unauthenticated like the current ones, so registry writes must never auto-approve.
   - **Client side.** A local outbox flushes silently; a hidden Advanced section can show history.

8. **Recommended implementation phases.**
   - **Phase 0 (small, first):** reset `pureCopyText` on the empty path and add the "anything to render" seam. This fixes the stale-text hazard and slightly changes System behavior, so it needs your OK.

   - **Phase 1B:** job intent, scope terms, intro composer, wording template keys, brand / model and marker polish.
   - **Phase 2:** local Custom Catalog with explicit save, soft delete and restore.
   - **Phase 3A:** frontend-only Device ID and `provenance`. It is independent and can move earlier.
   - **Phase 3B:** backend registry action, three Sheet tabs and the outbox.
   - **Phase 4:** admin approval, shared delivery and promotion into built-ins.
   - **Dependencies:** 0, then 1A, then 1B; 2 after 1A; 3A after 0; 3B after 3A; 4 after 3B.
   - **Open decisions** (also in the brainstorm record):
