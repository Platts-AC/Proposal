## Final Agent Report — Verbatim

**v10.02.05 is done: after the last selected system is removed, the proposal output is now cleared instead of left stale, so Create can no longer send an old proposal.** The fix sits in the renderers, behind one small "anything to render" seam that later Custom Proposal work can extend. Normal System Changeout output, Create, Update and the pricing snapshot are unchanged (compared against v10.02.04 request by request). The backend is untouched, and I did not commit, push or deploy.

1. **Root cause of stale proposal output.**
   - **Where it came from.** `updateProposalCartUI` and `updateProposalTerminal` both returned early when `selectedProposalRows.length === 0`. The text that Create, Update and Copy use, `window.pureCopyText`, is only rebuilt further down, in the non-empty path of `updateProposalTerminal`. So it kept the last system proposal. The block lists (`window.proposalBlocks`, `window.lastRenderedBlocks`) had the same problem, and only the terminal placeholder and `cachedProposalText` were reset.
   - **Why Create sent it.** Create (and Update) only check that the text is not empty. They have no idea whether it still matches the selection.
   - **Reproduced.** The new test reproduces it on the v10.02.04 page: after the only system is removed, the old "System Option 1" text is still there and Create sends it with `selectedProposalRows: []`.

2. **Exact rendering seam introduced or changed.**
   - **New:** two small functions, placed just before `updateProposalCartUI` and also exposed on `window`.
     - `hasRenderableProposalContent()` returns true when one or more system rows are selected. A later proposal type changes only this function.
     - `resetProposalOutputState()` clears `window.pureCopyText`, `window.cachedProposalText`, `window.proposalBlocks` and `window.lastRenderedBlocks`, and restores the terminal placeholder (the same text as before).
   - **Changed:** the two row-count conditions. `updateProposalCartUI` now uses `if (!hasRenderableProposalContent())` for its sorter placeholder branch. `updateProposalTerminal` now starts with `if (!hasRenderableProposalContent()) { resetProposalOutputState(); return; }`. Nothing else in the renderers was touched.
   - **Why in the terminal.** The terminal renderer is also called directly by many paths (Create's own job-data refresh, injector, templates, selection marker), so resetting there covers all of them, not just the cart redraw.

3. **Exact empty-state behavior now.**
   - **Output.** With no renderable content the terminal shows "Your customized proposal will compile here...", `pureCopyText` and the cached text are empty, and the block lists are empty.
   - **Create and Update.** Create is refused by the existing check ("Missing Date, Name, Address, or Proposal Output.") and sends nothing. Update would refuse in the same way ("Proposal Output is empty...").
   - **Working state stays.** The reset only clears rendered output. The scratchpads, the proposal state, the customer / job data, injected lines, overrides and settings stay as they were (verified against the v10.02.04 page).
   - **Smart Injector unchanged.** With no system a stored injector line is still not rendered. Injector-only proposals are not supported yet.
   - **Re-selecting a system** regenerates exactly the same output as the first time.

4. **Whether any Create defensive guard changed and why.**
   - **No change.** Create and Update are byte-identical.
   - **Reasoning.** With the root fix the output is empty whenever nothing is renderable, and Create's first action (its job-data refresh) re-runs the renderer, so even a stale text cannot survive to the check. A new "needs selected rows" check in Create would be redundant and would block future zero-row custom proposals; a type-aware check would have to call the same seam, which Create already effectively does through the output.
