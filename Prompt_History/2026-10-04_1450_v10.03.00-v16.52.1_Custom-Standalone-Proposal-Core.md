## Final Agent Report — Verbatim

**v10.03.00 is done: Custom / Standalone proposals now work end to end, with zero selected HVAC systems, as a second Proposal Type next to System Changeout.** You choose the type in the Actions area, build items in a new Custom Proposal panel, and get Combined Package, Itemized or Customer Options output. It saves, updates, loads and survives a refresh through the existing managed-proposal and draft paths with no backend change. System Changeout is unchanged (compared with v10.02.05 request by request). One deliberate difference from your preferred wording: the Custom file name is `<date> - <customer> - Custom - Proposal`, not `... - Custom Proposal`, because the exact form needs a backend change (details in item 8). I did not commit, push or deploy.

1. **Proposal Type implementation.**
   - **State.** `proposalAppState.proposalType` is `"system"` or `"custom"`; a missing value is System, so every older proposal loads unchanged. The key is created only when someone switches type, so a System proposal's saved state is not altered.
   - **Control.** A new Proposal Builder component, `control:proposalType` (a select: System Changeout / Custom / Standalone). It is a parked original node like the destination select, allowed in Actions or a band, and the component table now has 21 components.
   - **Placement.** The built-in Desktop layout puts it in Actions (the first cell of the third row of the first column); the built-in Mobile layout adds a row after the destination. Both add one row to the built-in default Actions area (about 30 px on Desktop, 34 px on Mobile).
   - **Layouts.** Layout data goes from revision 5 to 6 (schema stays 3). An older saved layout gets the control once (the first empty Actions cell, else a new Expanded-only band), the saved layout is not rewritten until it is edited, and a layout that leaves it unplaced keeps it unplaced. Nothing forces a reset. A loaded Custom proposal works even when the control is not visible, because the panel follows the saved type.
   - **Switching.** Switching System -> Custom -> System keeps both modes' state: the selected system, its scratchpad and injected lines while Custom is active, and the custom items while System is active. In Custom mode the Smart Scope checklist and the Systems Sorter are hidden (never emptied); switching back restores them.

2. **Custom Proposal state model.**
   - **Structure.** `proposalAppState.customProposal` = `{ schemaVersion: 1, intent, scopeTerms[], presentation (combined | itemized | options), packageTitle, items[] }`. `intent` and `scopeTerms` are stored and sanitized but have no UI yet (Phase 1B).
   - **Item fields.** Each item is `{ id, genericType, action, name, description, brand, model, price (number or null), role, marker, catalogRef (null) }`. The item owns its values, so a saved proposal never depends on a local catalog. `role` and `marker` follow the presentation (package / line / option, none / selection).
   - **One sanitizer** serves the live state, the working draft and managed Load. It uses fixed keys only (no unknown or prototype keys), known enums, unique safe ids, non-negative numeric prices (text prices and negatives become null, 2 decimals), removes control characters, caps lengths (name 160, description 4000, brand and model 80), keeps at most 40 items and drops non-objects (with a note).
   - **Text is data.** In the terminal it is escaped (tested with markup in an item name); the Create and copy text keep exactly what was typed.

3. **Custom builder UI.**
   - **Where.** A collapsible "Custom Proposal" panel in the Page 2 body, between the Customer panel and Smart Scope. It shows only in Custom mode, is not part of the grid, and its header shows "N items · presentation · total".
   - **Fields.** A presentation select and a package title; item cards with Generic type, Action, Proposal / display name, Description (a multi-line, paste-friendly box), Brand, Model and Price ($, typed text such as `$1,250`).
   - **Actions.** + Add Item, Remove and Move up / Move down per card.
   - **Typing.** Typing in a field updates the state and the output without rebuilding the card, so the caret is never stolen; adding, removing, moving, a type switch, Load, draft restore and New Quote do rebuild it.

4. **Combined / Itemized / Options output behavior.**
   - **Blocks.** Custom blocks use their own targets: `Custom Intro`, `Custom Package`, `Custom Item N`, `Custom Option N`, `Custom Total`, `Custom Closing`. The Customer Information block, ordering, drag, the Focus Editor, overrides and injected lines are reused. The Smart Injector renders after the custom blocks as before, and an injector line without a custom item still renders nothing (no injector-only proposals).
   - **Combined Package.** One block with the title ("Proposed Work" if blank), each item (name, brand / model, indented description) and ONE Investment equal to the sum of the typed prices. Tested: $1,200 + $350.50 = $1,550.50.
   - **Itemized.** One block per item with its own Investment (omitted for an unpriced item), and a Total Investment block for two or more priced items.
   - **Customer Options.** Each item is an "Option N" block with the existing selection marker setting (checkbox, or the initial line) and its own Investment.
   - **Pricing.** The System pricing engine, site, crane, refrigerant, Smart Scope and pricing snapshot code is never used for Custom (a static check scans the new code).
   - **Wording.** Baseline wording is intentionally plain: "We are pleased to offer you a quote for the following work." and no closing text. An optional "Custom Proposal Closing Text" entry was added to Default Proposal Wording and is empty by default, so no warranty claim is assumed.
   - **Focus Editor.** For custom blocks the Focus Editor edits the whole block, price included. This needed one condition on the System code: the "strip the Investment" rule now skips targets starting with "Custom ".

5. **Render eligibility changes.**
   - **System.** `hasRenderableProposalContent()` is true with one or more selected rows.
   - **Custom.** It is true when at least one item has a name or a description (after sanitizing).
   - **Empty panel.** A Custom proposal with no items or only blank items is not renderable, even if a System selection exists in the background. The Phase 0 `resetProposalOutputState()` clears the output (placeholder, empty text, no blocks) and Create is refused without sending anything.
   - **Dispatch.** `updateProposalCartUI` dispatches Custom to its own block builder before any of the System composer runs. The Phase 0 stale-output fix still holds.

6. **Managed Create / Update / Load behavior.**
   - **Create.** Create with a Custom proposal and zero system rows is accepted. The request carries the custom state inside `proposalAppState` (type custom, items with their typed values), `selectedProposalRows: []`, no scratchpads, no pricing snapshot, and the typed proposal text.
   - **Update.** Update saves the current custom state as the next revision with the normal revision handling (loaded revision 1 -> Rev 2). The backend accepts both unchanged: its Update check needs only a `proposalAppState`, a truthy `systemScratchpads` object and a `selectedProposalRows` array, which `{}` and `[]` satisfy.
   - **No snapshot.** The pricing snapshot is not attached for a Custom proposal (one guard line in `attachPricingSnapshot`).
   - **Load.** Load sanitizes through the normalizer (a damaged saved state is repaired and noted in the warnings). It restores type, presentation, title, item order and values, and regenerates the output with zero rows. A custom-only proposal does not require the equipment catalog and the "no selected options" warning is skipped for Custom (both by code, not separately tested).
   - **Confirmation.** The Load confirmation is type-aware. A Custom proposal shows Type, Items, Presentation and Total ("N of M priced" for Customer Options) and a notice that the prices are typed values and nothing is re-priced.
